# 使用入口、任务地图与检索成本

`v2026.11.12.3` 改善已有资料的查找、阅读与检索开销。本轮没有增加研究数量：仍为 296 条登记知识（64 基础、13 Native AI、110 Core、109 机制研究），机制族包含 404 项 API 合同。这些数量不代表全库 API 总量或游戏源码覆盖率。

## 从开发任务找到已有依据

[开发任务地图](../references/task-map.md)将常见功能接到相关指南和登记 ID，逐项说明已有局部合同、项目所需信息、未知范围与下一步验证。先按自己的任务选入口，再沿关键消费者补读，避免从整张目录开始猜知识族。

[检索策略](../references/kb-retrieval.md#研究记录怎样支持当前开发)说明从研究问题到当前源码核查、Mod 适用条件和行为验证的衔接。历史 ID、Scope、更正和 Coding HOLD 保留；研究导航与当前源码依据分别标注，未核实的行为继续列为缺口。

## 文件阅读的简短入口

无需配置 MCP 或准备来源，即可从包根运行：

```text
python -B -X utf8 run_kb.py find "OceanFishingTackle:SetupLure"
python -B -X utf8 run_kb.py read EXP-FISH-001 --pointer /api_contracts/2 --max-bytes 24000
```

两条命令复用现有公开目录审阅，按 ID 处理登记族的文件位置。机制研究按完整原子交付，其他公开记录按所选 JSON 值交付，并携带记录 Scope、状态和更正；读 Core claim 时应选择完整 claim，子字段不代表完整合同。响应明确说明未恢复或核验源码，不交付 Coding 上下文。正文过大时按返回指针续读；完整 MCP 的来源解析、API 消歧和角色约束继续适用。详细用法见[知识读取](knowledge-integration.md)。

## 检索计算

复杂任务装包会多次试算预算，并重新检查已选内容的导航覆盖。此次复用现有的单次请求缓存，保存相同文本的主题和导航词项分析；请求结束即清空，返回的集合彼此隔离。来源内容哈希、环境校验、权限、完整原子预算和最终响应继续逐次处理。

本机用同一份 296 条 prepared 输入、同一隔离索引和同序请求，对照改动前后的直接 Service 调用。两侧都使用相同分段计时、关闭 cProfile；下表每个任务每侧各一次，不是多次平均，也不包含模型思考和客户端往返。

| 任务 | 改动前 | 改动后 | 耗时减少 |
|---|---:|---:|---:|
| 耗油装备、发射与冷却 | 195.156 秒 | 128.661 秒 | 34.07% |
| 双端信标与重新配对 | 137.655 秒 | 68.624 秒 | 50.15% |
| 可维修拟饵与本轮鱼获 | 99.009 秒 | 25.490 秒 | 74.26% |

三份响应的 UTF-8 字节哈希逐份相同。导航覆盖累计耗时从约 62～67 秒降到约 3～4 秒，完整性检查仍每题执行两次，合计约 0.35 秒。剩余耗时包括排名和合同匹配，复杂首包仍可能较慢；本次样本不保证所有问法获得相同比例的提升。

## 本轮边界

当前入口的版本、数量和源码范围说明已统一；历史阶段报告保留当时数字。没有全量改写登记记录，没有新增游戏运行结论，也没有因本轮优化授予研究条目 Coding 准入。后续完整功能链与源码拓展按任务地图中的实际缺口推进。
