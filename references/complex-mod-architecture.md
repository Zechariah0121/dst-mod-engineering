# 复杂 Mod 的模块边界与协作

适用于角色同时包含资源数值、多个法术、特殊装备、HUD、长期效果和存档恢复时的设计、接手与重构。目标是让状态写入、调用依赖、取消和恢复能被追踪；文件数量或目录深度不是验收指标。本文给工程建议与示例，不要求统一目录、全局事件总线或 Installer，也不替项目决定数值、玩法与失败补偿政策。

本轮于 2026-11-05 只读核对源码及既有参考，未运行游戏或附件测试。原生文件字节身份与逐项范围见文末 N01–N09；露露方案以 LULU 案例身份引用，不充当原生 API 事实。既有 canonical、Scope、HOLD 保持原样；本篇是工程参考；配套原版研究 EXP-ARCH-001 至 004 已单独登记，按[研究入口](../docs/phase7-architecture-native.md)显式审阅，不因阅读本篇解除 HOLD。

## 先决定边界，再移动文件

**工程建议。** 先给每项功能写五件事：谁拥有状态、谁能提出修改、谁只读取、从何时到何时有效、失败或加载后谁恢复。然后按真正不同的职责拆分，而不是每增加一个函数就建模块。

| 值得拆开的信号 | 通常保留在一起的情况 |
|---|---|
| 同一功能有客户端输入、服务器结算、HUD 三种执行环境 | 同一端、同一实体、同一寿命内的一组短小辅助函数 |
| 资源值、物品身份、长期效果有各自保存与清理责任 | 只为把几行条件转发到另一个文件，没有独立语义或验证价值 |
| 两个法术重复实现已稳定的校验/消费接口 | 只是动作外形相似，目标、部分成功和退款规则仍不同 |
| 一个全局文件同时改配置、装 Hook、运行结算、布局 UI，改动互相牵连 | 小功能入口本来清楚，局部函数和一份清理函数已能表达完整链路 |

拆分要解决明确问题：例如让 HUD 不必载入施法实现，让资源上限只在一个业务入口规范化，或让旧任务无法结束新效果。只增加转发表、字符串事件名和跨文件跳转而没有减少这些风险，就是过度设计。此判断是工程取舍；其依据是 N01–N04 的阶段/装配边界及 LULU-01/05/06 的失败案例，不能反推原版要求这种目录。

## 一个多功能角色的职责表

以下假设角色有魔力、若干法术、成长装备与徽章，仅用于说明职责；名字、数量与玩法都不是需求。角色组件不必按表逐行拆成文件；两个职责确实共享寿命和修改原因时可以合并。

| 职责 | 合理持有的数据/操作 | 允许的依赖与边界 |
|---|---|---|
| 入口与装配 | 当前阶段要注册的资源、Hook、组件连接 | 依赖功能登记入口；不持有全体玩家的运行状态。前端、worldgen、进世界分别核对（N01，LULU-01） |
| 定义与规则 | 法术标识、描述、已确认的费用/目标规则 | 优先表达数据或明确输入的计算；不在读取一张定义表时悄悄注册 HUD 或扫描世界。动态规则通过参数读当前状态 |
| 权威资源组件 | 当前值、上限、合法修改方法、持久化数据 | 多个恢复/消耗来源调用同一修改合同；HUD 不直接写该组件（N03；[数值接入](spells-and-custom-stats.md)） |
| 一次施法的业务编排 | 校验、调用资源/效果接口、记录本次结果 | 由实际 Action/SG 执行入口调用；明确拒绝、部分提交和中断语义，不包揽所有功能保存（N07，LULU-03/04/10） |
| SG 与表现适配 | 当前动作阶段、动画/声音/FX、局部任务 | 调业务接口并读取结果；不靠动画结束推定业务从未执行。清理只释放本状态持有的表现（N05–N06，LULU-02–04） |
| 装备/长期效果 | 物品自身身份、耐久/阶段、效果来源和退出 | 玩家偏好归玩家、物品身份归物品；共享原版属性使用适合的来源接口，不让多个模块盲目恢复旧标量（LULU-08–10） |
| 复制与读取视图 | 该功能实际需要的公开状态、可用性与读取接口 | 由权威写入驱动；视图存在不等于值已到达。不要给所有字段发明统一 ready 事件（N04，LULU-05/07） |
| 本地输入与 HUD | 当前本地玩家/Widget绑定、按钮、显示缓存 | 输入只发意图，显示读复制视图；重建时解绑旧对象、初读当前值。不能仅用“非专服”证明目标就是本地玩家（LULU-06/07） |
| 世界/分片协议（确有需要时） | 跨实体唯一性、预约、未决请求的恢复状态 | 只有确实跨角色/跨分片的约束才提升到这里；普通资源不要统一搬到世界账本。单分片权威不等于主分片协调（LULU-09） |

建议的**调用方向**是：输入 → Action/SG → 本次业务编排 → 资源、物品或效果的公开操作；权威状态 → 复制视图 → HUD。入口负责把这些对象在合法阶段连起来，定义/计算模块通常不反向导入 UI。这里是职责关系，不是完整网络时序图；预测端仍需沿原版动作链另核查。

### 贯通示例：从法典按钮到长期效果的恢复

设已有魔力组件、法典和徽章，现在增加一个带冷却的持续效果法术。费用、持续时间、死亡是否保留，以及效果失败时是否退款，都由项目先确认；这里不补数值，也不预设扣费顺序。用同一条业务链检查各模块是否接得起来：

| 阶段 | 谁做什么、交给下一段什么 | 失败/变化时由谁负责 |
|---|---|---|
| 选中与发起 | 本地输入选法术与目标，经现有动作/预测链提交意图；UI显示只是读取视图 | RPC/动作适配检查实际玩家、载体和输入；不能接受客户端直接上报的余额或成功结果（LULU-07） |
| 进入动作 | SG持有本次动作记忆与表现资源，绑定实际权威执行时机 | 起手期间目标、资源仍可变化；SG退出清自己的声音/FX，是否消费由业务所处阶段决定（N06，LULU-03/04） |
| 权威执行 | 本次业务编排重验玩家、目标、资源、冷却，调用资源与效果公开操作；记录已扣费用、已生效目标和冷却变化 | 执行顺序按项目合同；某一步异常后对照已发生的事实处理部分提交，不能把一个false当全部撤销（N07，LULU-10） |
| 发布与表现 | 权威组件发布相关复制状态；SG依据真实业务结果及当前执行权继续尾段；HUD初读并跟随后续更新 | 扣费事件若同步切态，旧SG不再启动表现，但已扣费用不因此自动再扣或自动退；HUD重建重新绑定当前对象（N05，LULU-03/06） |
| 到期与硬中断 | 效果所有者释放本来源修改器/任务；SG只清当前动作表现 | 玩家死亡、目标移除与取消各按已确认政策退出；不能因动作结束便删除设计要求继续的效果（N08，生命周期参考） |
| 保存与加载 | 资源组件保存资源事实，效果所有者保存合法恢复数据，冷却按既定时间政策保存；恢复阶段重建任务、视图与绑定 | 不重放首次施法费用；停止/接管构造期旧任务，目标引用缺失时按规则降级。若本效果本来不保存则不强加持久化（N08/N09） |

这条链允许小功能把“本次编排”留为一个局部函数；只有多入口、多状态或独立恢复责任确实出现时，才抽成专门模块。扩展第二个法术时，共享稳定的资源接口和复制读取，保留它不同的目标/消费/补偿规则；不用先搭一个能描述所有法术的解释器。

## 跨模块接口要暴露决定，避免泄露内部字段

**工程建议。** 对会写状态的接口，至少让调用方知道下表信息；这是设计检查表，不是必须实现的公共函数签名。

| 接口要说明 | 在多法术角色中的具体问题 |
|---|---|
| 执行端与前提 | 谁可调用，载体/玩家是否已装配，是否允许预测端调用，是否要求实际持有权 |
| 输入与范围 | 传实体还是ID，目标何时重验，材料从携带域还是打开容器取，有限数值如何校验 |
| 返回与副作用 | 拒绝原因、已消费/已产生的效果；是否同步发事件；异常时可能已改了哪些对象 |
| 生命周期 | 调用返回后原状态是否可能已结束；异步回调归哪个实体/本次尝试；如何取消 |
| 重复与恢复 | 再调用是更新、叠加、拒绝还是重做；保存后哪些事实足以重试，哪些必须保持未决 |

只读查询与执行命令可以是同一组件的不同方法，不必各建一层服务。查询返回的材料列表也不是预约；在执行时重新校验或显式定义预约政策。LULU-10 展示“同一材料域”仍不能解决 Hook/同步回调或多次扣料中途失败；不要由查询成功推导事务性。

对需要立即判断成功的局部操作，直接调用并获得明确结果通常比广播一个“请施法”事件更容易追踪。事件适合通知已发生的状态变化，或接入原版已约定的生产/消费链。若选择事件驱动命令，必须另外定义接收者、结果归属、重复、异常与取消，不能把 PushEvent 当消息队列或提交 ACK（N05，LULU-03/07）。不为仅有一个调用方的模块建立全局总线，也不禁止已有项目在明确合同下使用总线。

公共资源组件负责自身不变量；法术编排负责跨对象的一次业务关系。前者不应 require 某个按钮来刷新画面，后者不应绕过组件直接写资源内部表。Hook 尽量集中于目标条件、输入转换和转发，避免逐个 Hook 各自实现一套扣费/退款；小功能也可以在一个窄 Hook 内完成清楚的局部逻辑。模块名使用项目可辨识前缀，返回 API 与向 Mod env 登记副作用分开考虑；N01 的 modimport 不返回脚本结果，也不自动防重复执行。直接登记或显式 Install(env) 都可用，关键是阶段、消费者和真实安装目标的幂等性（LULU-01；[Lua 与 Hook](core-lua-hooks.md)）。

## 装配、时钟与执行权要能跨边界对齐

下列是**本轮核对的源码事实**，后列是基于它的工程建议，两者不能互相替代。

| 当前源码事实 | 对架构的影响 |
|---|---|
| AddComponent 调构造器后才写入 components，再调组件 PostInit（N02） | 构造期间使用 self，不从宿主字段取回自己；相互依赖的初始化放在依赖确实已装配的入口，不靠文件排列猜构造完成 |
| 角色工厂 common 位于 SetPristine 前，客端返回后才到 master；ReplicateEntity 建立所需 replica 后才调用 OnEntityReplicated（N03/N04） | 声明、构造、复制视图可见、业务装配是不同条件；按所需对象检测并处理重复绑定，不把“一帧后”当全功能已就绪 |
| EntityScript 普通监听直接调用，SG事件另有立即处理/入队分支（N05） | 每个可能发事件的外部调用都要审执行权；不要以“单线程”推断旧状态一定还在，也不把所有事件说成异步 |
| 有效 GoToState 先执行旧 onexit，后新建 statemem，再进入新态（N06） | 状态级回调可捕获本次 mem 并在返回后复核；跨状态效果需更长寿命的所有者，不把 statemem 当持久对象 |
| UpdateState 消费 dt；外层 Update 用 GetTime 差量且可能按未来事件请求睡眠（N06） | 列出 SG、动画、FX、任务与绝对冷却各用哪只时钟；动作变速不能自然扩散到所有独立任务或冷却 |
| RemoveComponent 与实体 Remove 走不同通知；Remove 会清实体监听/任务并通知组件与 replica（N02/N08） | 生命周期缩短到状态、组件或效果时，要清本 Mod 还持有的资源；不要误称实体销毁没有自动清理，也不要期待它替尚存活对象清理旧效果 |

一次业务调用成功，与旧状态仍能继续播放表现是两个判断。LULU-03 中食物已消费，oneat 监听同步切到 hit，旧清理已完成；回调返回后再启动声音会制造清理后的副作用。正确的条件化处理是记录业务结果后，另检查本次表现所有者仍有效；不能因为失去表现执行权又消费一次。

同样，停止下一轮与结束当前已提交动作分开。LULU-04 保留已成功一口的既有尾段，同时让移动、受击、死亡等硬中断及时清理。是否保尾段、消费点和中断退款都是项目规则。详细时钟与同步边界直接读 [时钟与声音案例](lulu-clocks-sound.md)，不复制该项目帧数或倍率为通用架构常量。

为每个临时资源至少记录：所有者、创建点、自然结束点、硬中断点、重复安装处理，以及恢复字段时怎样确认仍是自己持有的值。同一资源不要同时归状态与独立管理器清理而没有交接合同。共享属性已有合适来源接口时复用它，不能为“单写者”架构强行夺取原版或其他 Mod 的字段；细节见 [生命周期](lifecycle-save.md)。

## 保存的是可恢复事实，失败政策要由业务明确

**源码事实。** N08 的 SetPersistData 在 prefab OnPreLoad 后，用 pairs 遍历组件 OnLoad，再到 prefab OnLoad；跨实体引用另有 LoadPostPass。不能依赖组件的固定加载次序。N09 的 timer 把剩余时间/暂停状态保存为数据，加载时停掉同名旧任务再重建，是本组件的范例，不能推广成所有效果离线计时方式。

**工程建议。** 让持有状态的组件保存自己的纯数据，跨模块恢复通过明确装配/恢复阶段协调。每份 schema 给出版本、缺字段默认值、合法范围与迁移规则；先恢复基础事实，再重算派生值、重建任务与复制视图。跨实体引用在适用的 postpass 中修复，缺失目标须降级；不要保存 Lua 对象、回调和任务句柄，或假设调用 OnSave 就已落盘。未知未来 schema 应按项目恢复政策保留或拒绝处理，避免悄悄降级覆盖。

加载时触发与主动施加时触发的业务不一定相同：恢复一个长期效果不该无意再扣一次初始费用；重建任务也不能叠加构造时已有的任务。迁移操作应能识别已迁移状态，原流程中可能产生奖励/物品的步骤单独防重复；具体保存签名和重启验收沿用 [生命周期与存档](lifecycle-save.md)。

| 失败发生在哪一段 | 必须作出的业务决定 | 不能自动推定 |
|---|---|---|
| 执行前校验拒绝 | 返回原因；不得产生该合同约定之外的消费/效果 | UI曾显示可用，所以本次必须成功 |
| 第一项副作用后失败 | 明确部分提交、可补偿还是保持未决；让调用方看见已发生的事实 | 返回 false 或 pcall 捕错会撤销此前写入（N07，LULU-10） |
| 已生成实体，交付背包失败 | 决定保留实体、落地或受控回收，并保留身份 | GiveItem失败意味着零实体，可以再生成（LULU-09） |
| 等待回应、加载恢复或分片失联 | 区分未知与已确认失败；按已持久化事实恢复同一请求 | 超时/本地没看到实体证明全局不存在（LULU-09） |
| 表现失败或旧状态已退出 | 记录业务结果，清理自己仍持有的表现资源 | 声音没播完等于业务未提交，应重新扣费（LULU-03/04） |

只有确实需要跨实体或跨分片不变量时才增加账本、请求ID或恢复 journal；它们需要对应的保存、去重和过期语义，不能只是装饰字段。LULU-09 的保守占用是项目的可用性选择，不是通用唯一性算法。世代号也可能随存档回滚，不能独立保证跨分片原子提交或恰好一次。详读 [事务与配料案例](lulu-transactions-crafting.md)。

## 怎样落到现有项目

1. 选一条真实用户操作画完整链：入口/输入 → 权威校验 → 效果与消费 → 复制读取 → 表现/退出 → 保存恢复；找出现在由多个地方重复写的字段。
2. 填职责表和接口前提；先沿用现有文件，只有上述边界确实不清时才拆。一个功能先形成可验证的纵向链，再抽取第二个功能真正共享的机制。
3. 在真实装配点连接依赖，验证服务端、远端和前端是否分别有合法对象；不要用全局初始化完成布尔覆盖多个实体与Widget重建。
4. 在可能发同步事件或跨帧的边界标出执行权与提交点，列出中断/重复/失败后的剩余状态，再整理任务和监听所有者。
5. 验证既有行为没有被文件移动破坏；按本次影响测试，不能仅因目录清楚就宣布架构改善已生效。

最小验收应能回答：重复装配是否只装一次；两个角色实例是否共享了不该共享的尝试状态；资源/目标在执行前变化是否重验；同步切态后是否再次生成旧表现；中断是否多扣或重复回调；旧档/缺字段/目标缺失是否安全恢复。界面另验真实远端、HUD重建和鼠标/手柄；存档另验保存后独立进程加载，跨分片承诺另做对应故障测试。历史替身、专服与 nosound 的证据边界沿用 [测试与发布](testing-release.md) 与 [夹具案例](lulu-fixtures-release.md)。本轮没有执行上述运行验收。
